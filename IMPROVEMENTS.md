# Security, Correctness, Architecture & Polish Improvements

This document provides a comprehensive log of every issue identified, the fix implemented, and the tests added or updated across all four refactoring phases.

---

## Phase 1 — Security Fixes

### 1. SQL Injection Vulnerability in Database Worker
- **Issue**: `db.processor.ts` interpolated unvalidated `schemaName` and `dbRole` strings directly into raw SQL template strings (`CREATE ROLE "${dbRole}"`, `CREATE SCHEMA "${schemaName}"`), creating potential for remote SQL injection attacks.
- **Fix**: Added strict allowlist identifier validation function `assertValidIdentifier` enforcing the regex `/^[a-z0-9_]+$/i`. Malicious inputs or non-matching characters throw an immediate error before any SQL statement is generated or executed.
- **Test Added**: In `db.processor.spec.ts`, added unit tests validating rejection of injection attack payloads (`"; DROP TABLE ...`, `"role' OR '1'='1"`, quotes, and semicolon-delimited SQL commands).

### 2. Plaintext Database Password in BullMQ Job Payloads
- **Issue**: `dbPassword` was generated by `project.service.ts` and placed directly into the BullMQ job queue payload (`CreateNewTenant`), exposing database credentials in Redis storage and logging pipelines.
- **Fix**: Removed `dbPassword` from `CreateNewTenant` interface and `createProject` queue payload. `db.processor.ts` now securely generates credentials server-side using cryptographically secure random bytes via `@baas/crypto-utils`.
- **Test Added**: In `project.service.spec.ts`, verified queue dispatch payloads no longer contain `dbPassword`. In `db.processor.spec.ts`, verified password generation and validation work seamlessly without payload reliance.

### 3. User Enumeration in `resendVerificationEmail`
- **Issue**: `resendVerificationEmail` returned different HTTP status codes and responses when an email existed versus when it did not, allowing attackers to discover registered user accounts. It also lacked per-account rate limiting.
- **Fix**: Standardized the endpoint to always return an identical generic 200 response (`"If an account exists with this email, a verification link has been sent."`) regardless of whether the account exists or is already verified. Added a Redis-backed per-account throttle (`throttle:resend-verification:<email>`) with a 120-second TTL in addition to IP throttles.
- **Test Added**: In `auth.service.spec.ts`, added unit tests asserting identical responses for existing and non-existing accounts, and verifying Redis throttle counter operations.

### 4. Session & Cookie Security Configuration
- **Issue**: Fastify session cookie attributes (`sameSite`, `secure`) used hardcoded values and did not fail fast if `SESSION_SECRET` was missing in production environments.
- **Fix**:
  - Implemented fail-fast validation in `main.ts` ensuring `SESSION_SECRET` is present and at least 32 characters in production.
  - Bound `cookie.sameSite` and `cookie.secure` to environment variables (`COOKIE_SAME_SITE`, `COOKIE_SECURE`) with production-safe defaults for cross-origin deployments.
  - Documented variables in `.env.example`.

### 5. Weak Password Policy
- **Issue**: Password validation in authentication DTOs allowed common dictionary words, short passwords, or repetitive patterns.
- **Fix**: Implemented a shared password validator (`password.validator.ts`) featuring `calculatePasswordStrength(password)` (scoring length, character classes, repetitions, and common dictionary entries) requiring score ≥ 3. Applied `strongPasswordSchema` uniformly across `RegisterDto`, `ResetPasswordDto`, and `ChangePasswordDto`.
- **Test Added**: Created `password.validator.spec.ts` testing scores for empty strings, common dictionary words, repeated characters, valid complex passwords, and boundary conditions.

## Phase 2 — Correctness & Robustness

### 1. CI Pipeline Services & Automated Migrations
- **Issue**: `.github/workflows/ci.yml` lacked active database services and migration deployment steps, leading to potential test divergence between CI and production.
- **Fix**: Updated `.github/workflows/ci.yml` with `postgres:16-alpine` and `redis:7-alpine` service containers, added healthy ping checks, automated Prisma migration deployment (`prisma migrate deploy`), and wired E2E test execution.

### 2. Session TTL Alignment
- **Issue**: Discrepancies existed between Redis session TTL, Fastify cookie `maxAge`, and PostgreSQL `Session.expiresAt`.
- **Fix**: Centralized all session TTL constants in `src/modules/auth/constants/session.constants.ts` (`SHORT_SESSION_TTL_MS`, `REMEMBER_ME_TTL_MS`, `DEFAULT_SESSION_TTL_MS`, `DEFAULT_SESSION_TTL_SECONDS`). Cookie `maxAge`, Redis key expiry, and DB records now derive from this single source of truth.

### 3. Atomic Cache Invalidation on Password Reset
- **Issue**: In `resetPassword` and `changePassword`, Redis session keys were purged before the database transaction committed. If the database update failed, cached sessions were lost or in an inconsistent state.
- **Fix**: Moved Redis session deletion to execute strictly *after* the Prisma `$transaction` resolves and commits.
- **Test Added**: In `auth.service.spec.ts`, added unit tests verifying that if the database transaction rejects with an error, `redis.del` is never called.

### 4. VerificationToken Uniqueness & Graceful Conflict Handling
- **Issue**: Concurrent verification requests could cause unique constraint race conditions or allow duplicate active tokens for the same user and type.
- **Fix**: Added compound unique constraint `@@unique([userId, type])` in `schema.prisma` with corresponding SQL migration `20261121150000_token_uniqueness`. Wrapped token creation with graceful conflict handling (`catch` fallback to `updateMany`).
- **Test Added**: Unit tests in `token.service.spec.ts` and `auth.service.spec.ts` testing concurrent generation and conflict resilience.

### 5. Idempotent GET Endpoints
- **Issue**: `getAllSessions` (`GET /api/v1/auth/get-sessions`) performed database writes (`session.update({ data: { lastActiveAt: now } })`), violating HTTP GET idempotency.
- **Fix**: Removed database writes from `getAllSessions`, making it purely read-only. Added a dedicated `@Post('heartbeat')` endpoint calling `authService.touchSession(userId, sessionId)`.
- **Test Added**: In `auth.service.spec.ts`, verified `getAllSessions` does not invoke `prisma.session.update`. Added unit tests for `touchSession` and the `heartbeat` controller handler in `auth.controller.spec.ts`.

## Phase 3 — Architecture & Maintainability

### 1. Centralized Cryptographic Utilities (`@baas/crypto-utils`)
- **Issue**: Duplicate implementations of `hashToken` and `generateCryptoToken` existed across `AuthService`, `ProjectService`, and worker processors.
- **Fix**: Created new workspace package `packages/crypto-utils` (`@baas/crypto-utils`) providing `generateCryptoToken`, `hashToken`, and `generateSecurePassword`. Updated all call sites across `auth.service.ts`, `project.service.ts`, and `db.processor.ts`.

### 2. Extracted TokenService from AuthService
- **Issue**: `AuthService` was bloated with low-level token lifecycle management, database transactions for verification tokens, and expiration checking.
- **Fix**: Extracted `TokenService` (`src/modules/auth/services/token.service.ts`) encapsulating `issueVerificationToken` and `consumeVerificationToken`. Injected into `AuthModule` and `AuthService`.
- **Test Added**: Created `token.service.spec.ts` covering token issuance, expiration validation, type mismatch checks, and graceful conflict resolution.

### 3. Presentation Logic Decoupled from ProjectService
- **Issue**: `ProjectService.getProjectOverview` synthesized UI-specific data, formatted byte strings, synthesized chart series, and assigned styling attributes (`tone`, `hideOnMobile`).
- **Fix**:
  - Extracted presentation logic into `project-overview.presenter.ts` (`presentProjectOverview`).
  - Stripped UI-specific fields (`hideOnMobile`, `tone`) from the API response DTOs.
  - Made `StatCard.tsx` in `app/web` default gracefully to `'success'` tone and handle optional mobile visibility in the presentation layer.
- **Test Added**: Created `project-overview.presenter.spec.ts` verifying bytes formatting, relative time calculation, and asserting that UI-only fields (`tone`, `hideOnMobile`) are excluded from API payloads.

### 4. Gated Mock Data in Production
- **Issue**: `mock-data.ts` in `app/web` automatically fell back to mock data if the API fetch failed, risking showing fake projects in production.
- **Fix**: Gated fallback mock data behind `process.env.NODE_ENV !== 'production' || process.env.NEXT_PUBLIC_ENABLE_MOCKS === 'true'`. In production, a failed fetch now raises an explicit error rather than silently serving mock data.
- **Test Added**: Created `app/web/src/features/project/mock-data.spec.ts` testing dev mock return and production error throw.

### 5. Documented Canonical Authentication Strategy & Swagger Schemes
- **Issue**: Ambiguity regarding stateful cookie sessions vs stateless JWT authentication.
- **Fix**: Created `docs/AUTH_STRATEGY.md` describing the dual authentication model. Updated Swagger `DocumentBuilder` in `main.ts` with explicit security schemes (`sessionId` cookie auth, `bearer-jwt`, and `api-key` header).

## Phase 4 — Polish & Hardening

### 1. Database Indexes on Session
- **Fix**: Ensured composite indexes for `Session.userId` and `Session.expiresAt` are defined in `schema.prisma` and generated in migrations.

### 2. Global Safe BigInt JSON Serialization
- **Issue**: `BigInt` values returned from Prisma queries for large counters caused `JSON.stringify` to throw `TypeError: Do not know how to serialize a BigInt`.
- **Fix**: Created `bigint-serializer.util.ts` providing `registerBigIntSerialization()`, `safeBigIntReplacer`, and `safeJsonStringify`. Enabled globally in `main.ts` at application startup.
- **Test Added**: Created `bigint-serializer.util.spec.ts` verifying safe serialization of large BigInt numbers and nested objects.

### 3. Environment Variable Reconciliation
- **Fix**: Created comprehensive root `.env.example` and updated `README.md` to reflect all configuration variables (`SESSION_SECRET`, `COOKIE_SAME_SITE`, `COOKIE_SECURE`, `DATABASE_URL`, `REDIS_*`, `FRONTEND_URL`, `CORS_ORIGINS`).

### 4. Pinned Docker Images & Dependabot Configuration
- **Fix**:
  - Pinned `node:24.18.0-alpine` in both `app/api/Dockerfile` and `app/web/Dockerfile`.
  - Pinned `postgres:16.8-alpine` and `redis:7.4.2-alpine` in `docker-compose.yaml`.
  - Created `.github/dependabot.yml` monitoring npm, github-actions, and docker ecosystems across the monorepo.
